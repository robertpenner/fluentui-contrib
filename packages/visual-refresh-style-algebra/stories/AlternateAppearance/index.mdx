Earlier cross-engine research recorded a puzzle: under `forced-colors: active`,
Chromium and Firefox painted an **unselected primary ToggleButton** and a
**secondary Button** identically, while WebKit did not. It was filed as a
browser divergence. It was two things, and only one of them was the browser.

## The CAP defect

Upstream Fluent gives primary ToggleButtons a deliberately different
forced-colors treatment from primary Buttons, with the reason written down:

```ts
// Do not use primary variant high contrast styles for toggle buttons
// otherwise there isn't enough difference between on/off states
const usePrimaryHighContrastStyles = makeStyles({
  base: {
    '@media (forced-colors: active)': {
      backgroundColor: 'ButtonFace',
      ...shorthands.borderColor('ButtonBorder'),
      color: 'ButtonText',
      forcedColorAdjust: 'auto',
    },
  },
});
```

CAP replaces that block. Its copy restated the three colours — and dropped
`forced-color-adjust: auto`. That mattered, because CAP's *Button* primary block
contributes `forced-color-adjust: none`, and CAP's ToggleButton hook runs the
Button hook first. With nothing restating the opt-in, the two declarations sat on
the same root at the same specificity, `mergeClasses` had no matching key to
collapse, and the winner was decided by **stylesheet insertion order**:

```css
@media (forced-colors: active) { .f1h3a8gf { forced-color-adjust: none } }  /* CAP Button, primary */
@media (forced-colors: active) { .fg4l7m0  { forced-color-adjust: auto } }  /* Fluent ToggleButton, primary */
```

The same button computed `auto` or `none` depending on what else the page had
rendered first. Measured alone it read `auto`; measured after another CAP
fixture it read `none`. A component whose accessibility behaviour depends on its
neighbours' render order is not configured — it is undefined.

The fix is one line: CAP's ToggleButton forced-colors block restates
`forcedColorAdjust: 'auto'`, exactly as upstream does. Restating it also gives
the declaration the same Griffel key as the `none`, so `mergeClasses` now
collapses the pair instead of leaving both on the root.

## The browser difference that remains

With the policy pinned, Chromium and Firefox agree that the two alternate
appearances paint alike, in both render orders. WebKit still disagrees, and the
reason is now readable rather than mysterious:

- WebKit **matches** `(forced-colors: active)` under emulation but does **not
  perform substitution**. The canary in the fixture below carries authored
  colours and no forced-colors treatment; in WebKit it survives untouched.
- The unselected toggle therefore lands on the system-colour keywords CAP names
  *explicitly* (`ButtonFace`, `ButtonText`, `ButtonBorder`), which every engine
  resolves.
- The secondary Button has **no forced-colors treatment of its own**, so with no
  substitution it simply keeps its authored greys.

So the agreement in Chromium and Firefox was never a CAP guarantee. It was the
engine doing the work that CAP's non-primary appearances leave undone. That is
the finding worth carrying forward: CAP declares forced-colors behaviour for
`primary` and `tint` and relies on user-agent substitution for everything else.

## How the law is stated

The executable law does not branch on a browser name. It reads the canary and
branches on the **capability** — does this engine substitute? — which keeps the
assertion true of any future engine that changes its mind, and stops one
emulated system palette from being treated as universal.

Both render orders are asserted, each in its own page, because Griffel's cascade
*is* its insertion order: mounting both orders on one page would let the first
decide the outcome for the second.

`forced-color-adjust` assertions are skipped where the engine does not implement
the property at all, which is checked with `CSS.supports` rather than assumed.
