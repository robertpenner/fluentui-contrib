The [Case census](?path=/docs/packages-visual-refresh-style-algebra-case-census--docs) begins with twelve clean-room content and icon-placement pairs and keeps four. This page asks a different question: what does the public Fluent Button actually accept, normalize, and render when VR CAP styles it?

## What is grounded

The table exercises the installed production pipeline rather than reconstructing its conditionals:

1. public `ButtonProps` construct each icon, children, and `iconPosition` scenario;
2. `useButton_unstable` supplies the normalized state;
3. `renderButton_unstable` supplies the rendered slot order;
4. CAP's `useButtonStyles_unstable` hook supplies the class effect.

The semantic table is verified by a component-level integration test running in the package's unit-test harness. Across all twelve scenarios, the test runs Fluent's public normalization and rendering functions, renders the public Button with and without CAP's style hook, and records slot presence, rendered order, and relative class changes. Generated class names are used only within the comparison; this page publishes their four stable semantic effects.

Because the test runs in a simulated DOM rather than a browser engine, it establishes normalized structure and style selection, not layout or pixel equivalence.

## What is interpreted

The clean-room mapping is deliberately separate. A **represented** row preserves the production distinction. A **canonicalized** row maps to a clean-room case while naming the production distinction it discards. An **unrepresented** row was observed successfully but has no clean-room content case.

None of those terms means product-supported. No product contract was found for these twelve scenarios, so support remains explicitly unknown.

The final table challenges the word “content” with real React child values. It records the point where input truthiness, CAP classification, and rendered DOM no longer agree, rather than forcing the empty-fragment case into one of the four clean-room configurations.
