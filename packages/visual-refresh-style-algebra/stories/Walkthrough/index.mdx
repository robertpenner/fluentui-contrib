<Title>Fluent and Visual Refresh: from styling changes to testable laws</Title>

A button change that begins as a new height or radius can spread through Fluent defaults, Visual Refresh changes, derived components, product requirements, interaction states, forced colors, and composite controls. **Forced colors** is the browser mode that adapts authored colors when a person uses an operating-system high-contrast theme. Once those layers overlap, it becomes difficult to tell which differences are intentional, which guarantees must survive, and which rule caused a regression.

[Why this research exists](?path=/docs/packages-visual-refresh-style-algebra-why-this-research-exists--docs) explains that practical problem and the tradeoff between retaining Fluent styling and reimplementing product styling.

This walkthrough introduces one response: describe **what must remain true** before deciding how to express it in CSS. That gives us a way to compare implementations, protect accessibility requirements, and investigate duplicated output without treating every generated rule as equally meaningful. You do not need algebra or property-testing experience to follow the approach.

## 1. Start with a situation, not a stylesheet

A button does not have one universal style. Its result depends on product, visual language, density, appearance, interaction state, environment, content, composition, and direction.

The model gathers those conditions into a **button case**. A resolver turns the case into a **style contract**: a structured answer describing geometry, color roles, focus, anatomy, and behavior. CSS comes later.

<CaseToContractExample />

The word _semantic_ matters here. `ButtonFace` means “use the system's button surface in forced colors.” It does not prescribe a hex value, a class name, or where a media query must appear.

## 2. Separate meaning from the route used to compute it

The package intentionally computes the same result in two different ways:

- The **layered resolver** begins with Fluent and applies ordered overrides. This resembles how a customization stack evolves in practice.
- The **semantic resolver** organizes geometry, appearance, focus, anatomy, and capabilities as separate decisions, then combines them.

The second implementation is a research comparator, not a recommendation to bypass Fluent styles. Neither architecture wins because its code looks cleaner. The useful question is whether a change in organization preserves the same user-facing result and must-always rules.

<ArchitectureExample />

This is why the technical stories show two buttons that look the same. Matching output is the expected result. The layered side additionally reveals which rule wrote a decision and what it replaced; the semantic side makes replaceable choices easier to see.

## 3. Turn design intent into laws

A screenshot can show one result. A **law** states what must remain true across many results.

Examples from this research include:

- compact density may change geometry, but not semantic color;
- RTL composition must preserve the correct outer corners;
- an icon-only button must retain an accessible-name source;
- forced colors must preserve focus, a visible boundary, and approved system roles.

The property tests generate valid button cases and challenge each law repeatedly. A passing run is evidence over those generated cases, not a mathematical proof or browser certification.

<LawExample />

The toggle introduces a deliberate teaching fault. The rendered button is less important than the contract observation: a product token appears where only system roles are allowed. That is the kind of regression a law can catch even when visual inspection is unreliable.

## 4. Keep accessibility policy above CSS emission

When an operating-system high-contrast theme activates forced-colors mode, authored colors may be replaced by a restricted system palette. Supporting that user need has two distinct levels:

1. **Semantic policy:** foreground, background, boundary, focus, and disabled distinguishability.
2. **Emission:** media queries, selectors, slots, declarations, specificity, precedence, and order.

The first says what must be preserved. The second says how a styling system represents it. Repeated `@media (forced-colors: active)` blocks may indicate harmless emitter duplication, a missing semantic abstraction, or necessary contextual variation.

<EmissionExample />

The experiment therefore normalizes conservatively. It removes only rules whose modeled context is equivalent. Similar declarations remain separate when selector, component, slot, specificity, precedence, order, or declaration behavior differs.

## What this work can and cannot claim

The model makes assumptions explicit and turns them into executable questions. It can show that two resolvers agree under the modeled contract, that deliberate faults are detected, and that some synthetic duplicate rules are safe to remove.

The runtime experiment captures Griffel output for public CAP Button-family fixtures and feeds it into the existing emission model unchanged. None of the 235 captured rules can be removed by the conservative normalizer. Differential fixtures show that disabled, selected, and alternate appearances replace generated atomic classes and rule context rather than merely activating one shared rule. Separate browser-emulation checks confirm selected and disabled paint relationships, but do **not** prove pixel-perfect production behavior, screen-reader output, the complete CSS cascade, or a real operating-system high-contrast session.

It also cannot decide what Teams, SharePoint, or another product should require. The model can expose a disagreement and test an agreed decision; product alignment remains a human responsibility.
